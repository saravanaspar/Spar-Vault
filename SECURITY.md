# Security status and boundaries — Spar Vault

This is a development implementation, not an independently audited password manager. Tests and compile checks cannot establish “fully secure” or comparative “most secure” status. Use synthetic credentials until independent review and device release testing are complete.

## Unlock and irrecoverability

Creation generates a uniformly random 32-byte root key with `Random.secure()`. The 64 hexadecimal characters encode that key; they are not a human password or wallet seed. Secure-key unlock always remains available. Explicit copy/save creates an **unencrypted** external key copy. Anyone with that copy and a vault snapshot can open it; store it separately and privately.

Folder-based key export replaces the exact `spar-vault-master-key.txt` in the selected folder. Preserve older keys separately if old backups still need them, especially before rotating the root key. Existing numbered exports are not automatically deleted because they may be the only recovery keys for older vaults. Browsers without folder-writing support can request a download but cannot control the browser's duplicate-filename policy.

Optional password unlock wraps this same random root using Argon2id v1.3 (19,456 KiB / 19 MiB, 2 iterations, 1 lane, 32-byte output) and AES-256-GCM. The salt is 32 random bytes and the nonce is 12 random bytes per wrapper. The fixed bounded profile meets OWASP's minimum Argon2id profile; it is not a claim of optimal cost on every device. The password must be unique and at least 15 characters. Offline attackers can copy and guess against the wrapper; app delays or lockouts would not stop that. No HKDF-only password derivation, raw password storage or recoverable password hint is added.

Password-wrapper AAD is the exact UTF-8 string `SparVault/password/v1|<vaultId>|Argon2id|19|19456|2|1|<base64-salt>`. Parsing accepts only that fixed profile, bounded canonical fields and the current version before allocating KDF work. Wrapper authentication and inner-vault authentication both must succeed. Native KDF work runs through Flutter compute; browser compute shares its event loop, so busy UI can pause briefly during derivation.

Android biometrics are a separate opt-in unlock path. A device-wrapped root is stored only after a **strong** biometric-authorized AES-GCM operation with an Android Keystore auth-per-use key verified to reside in TEE/StrongBox. The prompt uses a cipher CryptoObject, not a boolean success check. AAD binds the vault ID. There is no weak biometric or device-PIN fallback through the biometric-only binding. An independent, explicitly enabled **System lock** binding accepts strong biometrics OR the system PIN/pattern/password on Android 11+. It uses a separate hardware Keystore auth-per-use AES-GCM key, a cipher CryptoObject, a separate ciphertext slot and `device-lock` AAD. Anyone who knows the phone screen credential can use this binding; the app never receives or stores that credential. This is local device unlock, not a WebAuthn passkey or cloud-synced credential. Removing the screen lock, hardware failure or OS key invalidation requires the vault password/key. Both bindings are removed on restore/rotation. Keys must have hardware-enforced authentication and the exact allowed authenticator mask. New bindings require per-use authentication: creation uses timeout 0 and Keystore introspection accepts the documented -1 or provider-reported 0 representation. Old 30-second System lock bindings remain readable through their existing hardware authorization policy; explicitly replacing the binding upgrades it to per-use authorization. Authenticated AAD updates occur only after Android returns the authorized cipher. Enrollment changes/device binding failure require the original password or key. Only ciphertext/nonce/vault ID are retained in app-private preferences; OS app backups are disabled. Web System lock is unsupported.

Desktop System lock uses the dedicated `spar/system_lock` channel. Windows requires the Microsoft Passport provider, hardware implementation, mandatory per-use cache policy and a fresh gesture for actual RSA-OAEP SHA-256 decryption. A SID/vault-scoped protected key encrypts a payload containing the vault ID and root; enrollment verifies authorized decryption before committing ciphertext. No software-provider fallback is used. Linux verifies a PIN-and-touch ES256 FIDO2 assertion, credential identity and signature before using its 32-byte hmac-secret as an AES-GCM wrapping key. The exact AAD is `SparVault/system-lock/fido2/v1|<vaultId>`. Only public credential metadata and encrypted root/nonce/tag are saved. PINs are never command-line arguments or stored credentials. macOS uses a non-synchronized Data Protection Keychain item with WhenUnlockedThisDeviceOnly and userPresence access control; a fresh LAContext retrieves the actual 32-byte root. A valid signed application identifier is required. Unsupported providers fail closed.

Desktop enrollment is transactional; cancellation/session epochs reject late results. Linux/Windows local bindings are bounded, versioned, vault-scoped and reject symbolic links. Cancellation discards output; underlying Windows prompts may require the user to cancel the OS dialog, and FIDO operations finish within their native timeout. Native memory is cleared where feasible, but library/OS/managed copies cannot be guaranteed erased. Local administrative compromise remains outside these protections.

**If a password, biometric or System lock path still works, losing the key file alone does not make the vault inaccessible. Losing every enabled unlock method leaves no provider reset, escrow, support or email recovery.** Deleting the vault without a backup loses its data even if credentials remain.

## Vault protocol and migration

- Inner encryption keeps the legacy v1 framing for compatibility: HKDF-SHA256 derives an independent 32-byte encryption key on every save, with a fresh random 32-byte salt and info `SableVault/v1/encryption/<vaultId>`.
- AES-256-GCM uses a fresh 12-byte nonce and 16-byte tag. Inner AAD remains `SableVault|1|AES-256-GCM|HKDF-SHA256|<vaultId>|<revision>|<base64-salt>`.
- Payload JSON is prefixed by unsigned 32-bit big-endian length and zero-padded to 4,096-byte buckets. Titles, usernames, URLs, notes, timestamps, settings, TOTP secrets, attachments, history, native signing pins and deletion records are encrypted.
- Schema 2 adds preferences, history, attachments and deletion metadata. Old schema-1 backups remain readable. A new outer `spar-vault-bundle` version 2 holds the inner envelope and optional encrypted password slot. No plaintext root/password is in it.
- Public data still reveals algorithms, random ID, revision, padded approximate size and whether password unlock is enabled. No precise-size or all-metadata concealment is claimed.
- Unknown fields/versions/algorithms, noncanonical encodings, duplicate IDs, overlapping live/deleted IDs and oversized values fail closed. Limits: 2,000 entries; ten history values/item; ten attachments/item; 2 MiB/file; 8 MiB total attachments; 16 MiB padded payload; 32 MiB bundle; 48 MiB transfer package.

The framing and transfer protocol are custom combinations of standard primitives, not a standardized interoperable vault format. The independent HKDF/AES fixture and RFC TOTP tests are validation, not an audit. Old apps cannot read newly saved schema-2 vaults; preserve a pre-upgrade backup for rollback. Storage paths, platform IDs and legacy cryptographic context are retained to avoid losing existing data. Display branding is Spar Vault; the logo assets are unchanged.

## Sessions and storage

The default inactivity deadline is five minutes, with configurable 1/2/5/10/15/30-minute options. Pointer events, hardware keys and software-keyboard text changes refresh it. Timers lock directly; resume also checks elapsed wall time, and a backward clock jump fails closed. Immediate background lock is an optional stricter setting. Its sole prompt exception covers an app-initiated cryptographic system authentication prompt, which can make the host inactive or open the system credential Activity. The privacy cover remains, autofill is cleared in the strict background state, and manual lock, detachment and the original inactivity deadline still cancel pending authentication. The Android native prompt also has a 90-second limit; success is accepted only after foreground return within five seconds and the original session epoch remains valid. Errors retain distinct cancellation, timeout, lockout, enrollment, blocked-app and invalidation codes. Stale Android callbacks cannot complete a newer prompt. Cancelled replacement enrollment retains the previous binding. With it off, minimizing retains decrypted state until expiry; a privacy cover hides rendered content. This convenience increases exposure if a device is stolen during the active window. It is the requested policy, not automatic biometric protection.

Locking invalidates session epochs, drops entries, destroys owned/pending keys, closes secret-bearing dialogs and terminates integrations/transfers. Pending KDF, save, restore or approval work cannot reopen a locked session. A completed encrypted write/save may still finish after locking. Mutable byte buffers are overwritten where feasible. Dart/JavaScript/JVM strings, library copies, garbage-collected memory, OS swap/dumps, IMEs, debuggers and browser internals cannot be reliably zeroized. No guaranteed memory erasure is claimed. Android autofill drops JVM references on lock/expiry and uses monotonic time to expire its cache.

Native storage writes a flushed temporary encrypted file and renames it under an advisory lock plus per-isolate queue. Linux/macOS directories/files use 0700/0600. Windows inherits the user's AppData ACL; target installer/account ACLs need review. Android uses app-private storage. Directory metadata is not explicitly fsynced; power loss can still lose the latest change. CAS rejects ordinary stale writers but not administrator modification or rollback.

Web storage is one encrypted IndexedDB record updated in a transaction. Static service-worker caches hold public app assets only, never credentials or snapshots. Browser backups use a separate encrypted-only IndexedDB store where folder access is unavailable, but remain vulnerable to the same clearing/eviction. Folder permission may need renewing after reload. Automatic backups keep five copies with exact app/vault filename prefixes; unrelated files are not rotated. No independent backup guarantee is inferred from same-device copies.

Reveal lasts 20 seconds; clipboard clearing is attempted after 20 seconds and on lock, only if clipboard content still equals the value copied by this app. Clipboard histories, OS sync and other apps may retain it. Exported attachments and key files are plaintext external copies. The app cannot erase them or cancel every OS/browser download.

At the user's request, this build allows screenshots on every app page, including native Android autofill confirmation. Both Android activities clear FLAG_SECURE. Android disables OS backup/device transfer rules and keeps global cleartext network policy disabled. These controls do not defeat a compromised OS. Existing iOS hooks cover the switcher and apply file protection, but Apple builds are outside this update's validation. Linux/Windows screenshot protection is not promised.

## Backups, rotation and transfers

Restore first parses and authenticates the selected encrypted `.svlt`, then shows a preview and requires explicit replacement. Verification alone retains current storage. An imported `.txt` key alone is rejected with an explanation that the actual encrypted backup is also needed. Old backups use the credentials active when exported.

Rotation re-encrypts the live vault under a new random root, rewraps its optional password, and removes old biometric binding. It does not revoke already exported snapshots, delete old backup files or force another device to change its key. Export/verify a fresh backup. Pending foreign-key branches after rotation must use explicit restore; same-vault merge requires the current root.

Nearby v2 transfers expose only ephemeral receiver ID/public key/name/port through Android NSD and bounded UDP discovery. Names are informational. Both peers create fresh X25519 identities. HKDF-SHA256 binds both identities/public keys, sender name and item count; HMAC-SHA256 produces the six-digit comparison number. The user must compare the number on the actual two devices and approve on both. Discovery or a matching device name alone does not authenticate a peer.

Selected entries, including their attachments/history/TOTP, travel inside AES-256-GCM. AAD binds the full pairing transcript and message purpose (accept/items/receipt). No vault master key, password wrapper or preferences are transferred. The receiver imports entries atomically under its existing local root. Exact ID/content duplicates are skipped; changed-ID conflicts and previously deleted IDs become new copies, preserving existing entries/tombstones. This is an import, not automatic bidirectional synchronization or deletion propagation.

The receiver listens on local IPv4 for at most five minutes while the Receive dialog remains open. Requests reject Origin headers, non-private/noncanonical IP literals, unsupported methods/paths, oversized bodies, overlapping pairing and excess attempts. Approved payloads are consumed once before import. Lock/cancel invalidates epochs, closes sockets/advertising and destroys owned identities/session keys. Raw socket framing preserves Android’s global cleartext policy: the channel uses application encryption, not TLS. Local IP, public handshake/name/count and traffic size remain visible. Both devices need the same Wi-Fi/hotspot; this build does not negotiate Wi-Fi Direct, Bluetooth or create a hotspot.

The earlier v1 .svx/ticket implementation remains as internal legacy source/tests. Its typed-code/file/LAN controls are removed from the current UI. Durable backups use .svlt. Browser builds cannot discover nearby socket peers and retain encrypted backup export/restore.

Android QR scanning uses the local ZXing camera/image decoder, with no network lookups. QR-image input is limited to 8 MiB and sampled to approximately four million pixels. TOTP/Google export parsing is bounded and rejects malformed protobuf, unsupported algorithms, invalid page metadata and HOTP. Multi-page imports require matching batch metadata; only reviewed selected accounts are imported. Duplicate TOTP identities are skipped. Google migration is a reverse-engineered format, not an official stability guarantee. QR exports contain authenticator secrets and must be treated as credentials. Byte buffers are wiped where feasible; complete image/string erasure is not claimed.

## Autofill and web trust

Android native-app fill requires an explicit installed package plus exact current signing-certificate set in the encrypted item. Requests verify the framework caller, pins, field bounds and cache deadline, then use a nonexported secure confirmation activity with a private short-lived random request token. Only the selected username/password goes into a Dataset; no save-request collection or full-vault export is allowed. Website requests fail closed: Android's ViewNode strips the port, so a full origin cannot be established. Certificate pinning is explicit local app trust, not a Digital Asset Links assertion.

Desktop native messaging restricts allowed_origins to one extension ID, uses bounded little-endian framing, and forwards through a random loopback broker using a private expiring bearer token. It cannot bypass foreground approval. Lock deletes the state file and closes the broker. Same-user malware/administrators can read process state or attack an unlocked app; the token is not a boundary against that attacker.

The Chrome/Edge extension uses activeTab/scripting and optional vault-origin access for web mode, with no remote script or persistent secret store. It obtains the target's actual HTTPS origin from the browser, confirms a matching login in the vault, rechecks the origin after approval, injects only into the top frame and rejects ambiguous/cross-origin forms. Page script at the approved origin necessarily receives the filled values. Extension ID, nonce and same-window/origin validation restrict the web bridge; they do not isolate it from compromised first-party vault code. See `browser/README.md`.

A hosted website trusts delivered first-party code, including its updates/service worker. XSS, a malicious origin/update/extension or a compromised device can steal secrets while unlocked. CSP, bundled fonts/renderer, same-origin assets and no telemetry reduce exposure; they do not make malicious code safe. Prefer a controlled local build or independently reviewed signed native app for sensitive use. Keep a stable HTTPS/localhost origin and never serve backup/key files from its public assets directory.

Offline health is heuristic only, not a breach check or entropy proof. TOTP follows RFC 6238, needs an accurate clock, and storing it beside passwords reduces factor separation. Attachments are data only; this app does not execute or inline-preview them.

Independent review, device penetration testing, dependency/supply-chain review, signed packaging/update policy and incident handling remain necessary. Do not include real credentials in bug reports.

Primary design references: [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238), [Android autofill](https://developer.android.com/identity/autofill/autofill-services), [Android biometric authentication](https://developer.android.com/identity/sign-in/biometric-auth), [Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).

Restoring writes a fresh authenticated snapshot and resets device-specific automatic-backup/autofill settings. Re-enable them explicitly on the receiving device; passwords, entries, history and portable session/layout settings remain available.

## Android setup

`USE_BIOMETRIC` is a normal install-time permission; Android does not offer a standard runtime permission request for it. Enrollment/missing-screen-lock setup opens Android enrollment/security settings on an explicit user action. Blocked normal permission opens app settings; Android 16 biometrics-for-apps restrictions route to security settings. Unsupported hardware and device policy are reported, never bypassed with plaintext keys or a boolean-only authentication check.

Android autofill requires selecting Spar Vault as the system service, not a dangerous runtime permission. First enable launches the system service selector, waits for its result and checks `hasEnabledAutofillServices()` rather than trusting `RESULT_OK`. Rejection leaves a previously disabled app preference off. Resume refreshes service selection; revocation is visible in Settings and native cache updates clear credentials when the service is not selected. No accessibility-service or broad storage permission is required. The system document picker grants access to the selected file; encrypted payload validation and size limits remain mandatory. Local-network permission is requested before interface enumeration as well as socket use on Android versions that require it.

Installed-app selection lists visible launcher apps and automatically reads their current signing certificates. The user selects an app by name; no package-name entry is required. Certificate pinning and explicit autofill confirmation remain mandatory.

The JS release explicitly registers `spar_offline.js`. Its versioned cache has an exact allowlist of app HTML/JS, icons, font/asset manifests, bundled fonts/shaders and CanvasKit files. Only same-origin successful nonredirected public GET responses at these exact query-free paths are cached; private/no-store responses are refused. Snapshot/transfer URLs, arbitrary API responses, POSTs and user secrets are excluded. Cache eviction still prevents offline reload, and a web origin or delivered-code compromise remains a security risk. Bump the worker cache version with every release; the allowlist targets the validated JavaScript/CanvasKit build, not an untested Wasm release.

## Releases and vulnerability reports

Report vulnerabilities through the repository’s private GitHub vulnerability-reporting feature when enabled. Otherwise contact the maintainer privately through the repository profile; do not publish exploit details or vault credentials in an issue. Include a minimal synthetic reproduction, affected versions and expected/actual behavior.

GitHub CI tests all four shipped platforms before tagging the tested main commit. Android production signing requires repository secrets; the no-secret fallback is labelled Android_Test and debug signed. Desktop CI artifacts are unsigned Windows / ad-hoc macOS builds, without production notarization. Tags/checksums identify a build but do not substitute for independent review or signing. macOS System lock remains unavailable without the required signed Keychain identity. Preserve existing signing keys for upgrades.
